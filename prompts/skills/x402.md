题型 workflow：x402。目标是在 `{{challenge_path}}` 这个 x402 项目中完成安全审计并产出 findings。

核心目标是找出可验证、可复现、可解释影响的审计 findings。除非项目材料明确证明不是 x402/HTTP 402 payment flow，否则方向以 `--workflow x402` 为准。

适用范围：
- x402 payment middleware、facilitator、paywall、agent/client、wallet integration、settlement service
- 使用 HTTP 402、`X-PAYMENT`、payment requirements、EIP-712/签名授权、chain/token settlement 的项目
- 围绕支付绕过、验签、重放、金额/资产/收款方校验、网络/chainId 混淆、回调信任、facilitator trust boundary 的审计

工作要求：
1. 先读取题目目录中的 README、源码、测试、配置、Docker/compose、接口文档、示例请求和部署脚本
2. 在 `amds_state/cognition.json.metadata.challenge_type` 记录 `x402`，在 `amds_state/cognition.json.state.target_profile` 记录项目形态、关键入口和支付链路
3. 建立 payment flow map：resource -> 402 challenge -> payment requirements -> client payment -> facilitator/verify -> settle -> protected action
4. 标出 trust boundaries：client、resource server、facilitator、wallet/signer、RPC/chain、数据库、webhook/callback
5. 优先写最小复现脚本或测试，不要只写静态猜测；PoC 输出、HTTP transcript、测试日志统一保存到 `amds_state/evidence/`
6. 每个 finding 必须包含影响、前置条件、可复现步骤、证据路径、修复建议和置信度
7. 所有确认事实写入 `amds_state/cognition.json.facts`，审计假设、待验证路线和已拒绝路线写入 `amds_state/cognition.json.state`
8. 已验证 finding 写入 `wp.md` 的 `Findings` 小节；若是阶段性审计，也写 `Open Questions` 和 `Not Findings`
9. checkpoint 要按审计对象和 finding 粒度命名，例如 `x402-payment-flow-mapped`、`x402-requirements-binding-reviewed`、`finding-01-replay-verified`、`finding-02-fail-open-rejected`、`audit-report-ready`

重点检查：
- Payment bypass：未验证支付即可访问资源、只检查 header 存在、错误 fail-open、缓存绕过、路由漏保护
- Requirement binding：金额、token、recipient、chainId、resource、method、scheme、expiration 没有被完整绑定或被客户端可控覆盖
- Replay/double-spend：同一 payment 可跨资源、跨方法、跨用户、跨 chain 或跨时间窗口复用
- Signature/auth：EIP-712 domain 错误、nonce 缺失、deadline 缺失、签名主体和 payer 不一致、验签结果未绑定请求上下文
- Facilitator trust：盲目信任 facilitator 响应、verify/settle 不一致、回调无鉴权、错误处理导致 paid=true
- Settlement correctness：未等待确认、错误 token decimals、金额比较精度问题、recipient/asset 混淆、testnet/mainnet 混淆
- State/race：并发请求复用 pending payment、settle 前释放资源、支付状态 TOCTOU、幂等键设计错误
- Web/API 常规面：SSRF、open redirect、CORS、JWT/session、rate limit、request smuggling、prototype pollution、SQL/NoSQL injection

证据规则：
- 所有长输出保存到 `amds_state/evidence/`，例如 `amds_state/evidence/route-map.md`、`amds_state/evidence/payment-replay.log`、`amds_state/evidence/poc-bypass.txt`
- `amds_state/cognition.json.facts` 只写已验证摘要和证据相对路径
- `amds_state/cognition.json.capabilities[].evidence[].artifact` 使用 `amds_state/evidence/...` 相对路径
- 不要把私钥、token、cookie、助记词、真实支付凭据写入仓库；需要说明时使用脱敏值

完成标准：
- 至少完成源码入口、支付链路、trust boundaries、验证/结算逻辑和资源保护点的审计
- 对每个 finding 都有本地测试、脚本或命令输出支撑
- `wp.md` 中包含 Findings / Evidence / Reproduction / Remediation
- 如果没有发现有效问题，写明审计覆盖范围、已拒绝假设和剩余风险

执行约束：
- 不要攻击非授权目标，不要对真实支付网络执行会造成资金转移的操作
- 不要依赖公开审计报告或 issue 直接抄 finding；可以使用本地源码和项目文档作为事实来源
- 不要把“代码看起来可疑”直接当 finding，必须验证可达性和影响
- checkpoint 和回退统一遵守 `{{root_name}}/prompts/cmds/checkpoint.md`
